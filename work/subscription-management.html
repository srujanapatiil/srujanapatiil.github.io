Full-stack subscription management

Five self-service flows that let customers manage their recurring payments (list, detail, edit, pause and cancel), redesigned and rebuilt from TypeScript APIs through to a React Router application.

Organisation
The Shamaazi Project Ltd, UK fintech
Period
2023 – present
My role
Full-stack engineer, database to browser
Scale
50,000+ customers across 4 products

01Business context and problem

Customers with recurring payments need to see what they're paying, change it, pause it and cancel it themselves. Across four products and 50,000+ customers, every request that needs support staff costs time and trust.

The aim was self-service payment control: five flows that work the same way across products and stay consistent with the scheduling system underneath.

What the previous experience was like and why it needed redesigning (support load, inconsistent flows, an older app?).

02Engineering constraints and technical challenge

  • Correctness first: what the customer sees must match what the scheduler will charge next.
  • Four products, one codebase: shared flows with product-specific details.
  • Changes that touch money: edits, pauses and cancellations need clear confirmation and safe handling of repeated submissions.
  • Accessible on any device: keyboard, screen-reader and mobile use all matter.

04Individual contribution and collaboration

What I did

  • Worked across the stack, from the TypeScript APIs to the React Router app on AWS.
  • Evolved the PostgreSQL data model through 17 Drizzle ORM migrations for four products.
  • Introduced Playwright end-to-end tests for critical customer journeys.

Who I worked with

  • Product and Design on the redesigned flows.

05Key decisions and rejected alternatives

Chosen

One set of flows shared by four products, built against the same schedule APIs the scheduler uses.

Rejected

A separate management screen per product. Confirm, and add why.

Chosen

Entity-based database services with typed queries, so API handlers own HTTP and access control, and data access lives in one tested layer.

Rejected

Database queries written directly inside API handlers, which spreads data rules across endpoints and is hard to test.

06Implementation highlights

  • Five flows: list, detail, edit, pause and cancel, each backed by its own API operation.
  • Frontend: React and React Router in TypeScript, built with Vite and Tailwind CSS, and deployed on AWS.
  • Forms and UI: React Hook Form with Zod validation, on a shared component library built with Radix UI and documented in Storybook.
  • Data model: 17 Drizzle ORM migrations across four products, with entity-based services and targeted indexes.
  • Payment methods: changes handled through Stripe so card details never touch the application.

07Testing, accessibility and reliability

Testing

Playwright end-to-end tests for every critical journey, plus unit, integration and API tests in CI. Database integration tests cover the services behind each flow.

Accessibility

Semantic, keyboard-accessible UI that works on mobile and desktop.

Specific accessibility work (for example focus management in dialogs, screen-reader testing).

Reliability

Customer changes go through the same schedule APIs the scheduler reads, so what customers see matches what they will be charged.

Security

Customers can only see and change their own schedules; access control lives in the API layer.
