Cloud-native payment infrastructure

Event-driven, serverless payment APIs on AWS, defined as code with Terraform and shipped through GitHub Actions, plus a phased migration of services to TypeScript with the old and new stacks live throughout.

Organisation
The Shamaazi Project Ltd, UK fintech
Period
2023 – present
My role
Engineer on the serverless platform; led the migration to TypeScript
Scale
50K+ transactions at nightly peaks

01Business context and problem

Payment traffic is uneven. Most of the day is quiet; the busiest nights bring 50K+ subscription payments in a short window. The platform had to absorb those peaks without paying for idle capacity the rest of the time, and let the team change infrastructure safely.

At the same time, services were moving to TypeScript (Bun and Elysia). That migration could not interrupt live payments.

02Engineering constraints and technical challenge

  • Peaky load: capacity has to scale up for nightly runs and back down afterwards.
  • Reproducible infrastructure: every environment defined in Terraform and changed through review.
  • No downtime for migration: old and new services had to run side by side behind the same contracts.
  • Visibility for non-engineers: payment-run data needed to be queryable without asking a developer.

04Individual contribution and collaboration

What I did

  • Built and ran backend services in production, from REST APIs to event-driven Lambda functions.
  • Led the phased migration of live services to TypeScript (Bun, Elysia), keeping the old and new stacks live.
  • Created the data pipeline from DynamoDB to Athena that made payment-run reporting self-serve.

Team boundaries

The serverless platform is shared by a small team of 2–4 engineers; the outcome figures below describe the platform, not my work alone.

I wrote and extended Terraform modules and GitHub Actions workflows for the services I worked on.

05Key decisions and rejected alternatives

Chosen

Serverless functions behind queues, so capacity follows the nightly peak and a backlog waits safely in SQS.

Rejected

Always-on servers sized for the peak. That means paying for idle capacity most of the day, and more servers for a small team to patch and manage.

Chosen

A phased runtime migration, moving one service at a time behind its existing contract, with the old and new stacks running side by side.

Rejected

A single "big bang" rewrite and switch-over, which would put every payment path at risk at once.

Chosen

Athena over exported data for analytics, queried through Metabase, so reporting never touches the production database.

Rejected

Ad-hoc queries against production, which would add load to live payments and widen access to production data.

06Implementation highlights

  • APIs: REST endpoints and Stripe webhooks through API Gateway into Lambda.
  • Messaging: SQS for work queues, SNS and EventBridge for events and schedules.
  • Infrastructure as code: resources defined in Terraform and deployed through GitHub Actions CI/CD.
  • Migration: new TypeScript services on Bun and Elysia, introduced alongside the services they replace.
  • Analytics: a data pipeline from DynamoDB to Athena, with Metabase reports on top.

07Operations, monitoring and reliability

Resilience

Queues absorb bursts and retry failed messages individually; consumers are written to tolerate duplicate delivery.

Deployment

Infrastructure and application changes go through review and CI/CD rather than manual console changes.

Monitoring

CloudWatch for logs, metrics and alarms; Metabase for business-level views of each payment run.

CloudWatch alarms fire on API Gateway 5xx errors and on messages reaching dead-letter queues.

Testing

Unit, integration and API tests run in CI before deployment.
