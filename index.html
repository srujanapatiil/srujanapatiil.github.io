Scheduler

Runs on a fixed schedule, finds every payment due in this run and hands each one off as a separate unit of work.

Responsibility
Work out which schedules are due across daily, weekly, monthly and seasonal frequencies, skipping paused and cancelled ones.
Technology I've used
EventBridge schedules triggering TypeScript services; PostgreSQL holds the schedules.
Reliability
A run must be safe to repeat: one payment per schedule per due date, so a restart can't double-charge.
Trade-off
A nightly batch is predictable and easy to report on, but concentrates load into a short window.

Queue

Separates deciding what to charge from charging it, so one slow payment never blocks the run.

Responsibility
Buffer due payments and release them at a rate the provider and database can sustain.
Technology I've used
Amazon SQS feeding AWS Lambda consumers.
Reliability
Messages retry individually; repeated failures are set aside for investigation, not lost.
Trade-off
At-least-once delivery without ordering means every consumer must tolerate duplicates.

Payment API

Creates the charge with the payment provider for one schedule and one due date.

Responsibility
Create and confirm the payment with the right customer and payment method, and record the attempt.
Technology I've used
Stripe Payment Intents and subscriptions, integrated from backend services.
Reliability
An idempotency key from the schedule and its processing run makes a retried request return the original payment.
Trade-off
The API response is fast but not final; the provider's webhook is the source of truth.

Result handler

Receives the provider's events and turns them into the payment's final state.

Responsibility
Record succeeded, failed and refunded payments, then publish events for emails, analytics and retries.
Technology I've used
Stripe webhooks through API Gateway into Lambda; SNS and EventBridge for fan-out.
Reliability
Events can repeat or arrive out of order, so they're de-duplicated and state only moves forward.
Trade-off
Events keep features independent, at the cost of eventual consistency and more to monitor.

Retry workflow

Gives failed payments further chances to succeed, then stops cleanly.

Responsibility
Schedule retries, track each failure, and cancel the schedule automatically after the final retry.
Technology I've used
Payment-retry services across three subscription products; Stripe automatic card updates.
Reliability
Retries are capped and spaced out, and only failures that could succeed later are retried.
Outcome
In production this recovered 30% of failed payments.

How I engineer

Decisions, and why.

Questions that come up in payment systems, answered from work I've done.

Q1

Why process payments asynchronously?

A nightly run can reach 50,000+ payments. Doing them one after another makes the run as slow and fragile as its worst payment. A queue lets the scheduler finish quickly, lets workers scale with demand, and retries a single failure on its own instead of stopping the run.

From: recurring payments and AWS infrastructure work

Q2

How do you handle duplicate payment events?

I assume every message and webhook can arrive more than once. Payment creation uses idempotency keys so a repeated request returns the original charge, webhook handlers ignore events they've already recorded, and a payment's state only moves forward. Replaying anything should be harmless.

From: Stripe lifecycle integration

Q3

What makes a production database migration safe?

Small, reviewable steps that old and new code can both run against: add before you remove, backfill separately from schema changes, and add indexes deliberately on large tables. Every data-model change ships with integration tests against a real PostgreSQL database.

From: 17 Drizzle ORM migrations across four products

Q4

How do you migrate a runtime without disrupting customers?

Gradually, behind stable contracts. Moving services to TypeScript (Bun and Elysia), the old and new stacks stayed live side by side. Services moved one at a time with the same API contract, so each step could be verified and rolled back on its own.

From: phased migration to TypeScript
